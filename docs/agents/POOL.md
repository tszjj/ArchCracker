# 子智能体池与复用策略

本文规定 ArchCracker 项目中“什么时候复用已有智能体、什么时候新建”的默认规则。
它是 [`AGENTS.md`](../../AGENTS.md) §6.2 的展开，角色槽位与运行时无关；DSH 用
`list_agents`/`send_message` 实现复用，Codex/Claude Code 等按同一套槽位人工登记，
没有等价复用工具时再新建。

## 1. 目标

- **同类工作复用**：同一角色、同一领域的后续任务，优先回到已有智能体，而不是重新开一个。
- **上下文高效**：复用已读过仓库/任务/评审记录的上下文；新建只付一次“重新读仓库”的成本。
- **评审独立**：作者不复用为同一改动的 reviewer；需要独立判断时，换一个**同角色但未参与该改动**的已有 reviewer。
- **可审计**：每个智能体有稳定的角色/领域标签，能看出它为什么存在、下次该找谁。

## 2. 角色槽位

默认只保留这些槽位；同一槽位可跨任务复用，不按 PR 建新槽位。

| 槽位 | 典型职责 | 复用条件 | 新建条件 |
|---|---|---|---|
| `architect` | ADR、接口、跨平台约束、任务拆分 | 同一架构/契约议题的后续 | 需要独立架构评审且现有 architect 已参与该决策 |
| `researcher` | 技术调研、许可/平台/依赖比较 | 同一主题的后续调研 | 新主题且无相关上下文；或需要独立复现 |
| `core-engineer:core` | `acx-core` 引擎/调度/候选/FFI | 同一模块的后续实现、修复、测试 | 并行实现不同模块且互不阻塞 |
| `core-engineer:cli` | CLI、退出码、集成测试 | 同一 CLI 切片 | 与 core 改动并行且文件不重叠 |
| `frontend-engineer` | Avalonia/Compose/ArkUI、打包 | 同一前端切片 | 需要独立 UI 评审或不同平台 |
| `qa-engineer` | 语料、差分、模糊、基准 | 同一格式/同一基准的后续 | 需要独立复现且现有 QA 已参与实现 |
| `qa-engineer:gpu` | hashcat/GPU spike、CPU 回退验证 | 同一 spike/同一 GPU 结论的后续 | 需要独立性能/驱动验证 |
| `reviewer:core` | 核心正确性/性能/许可 | 同域后续 PR | 现有 reviewer 是该 PR 作者，或需要第二意见 |
| `reviewer:rar` | RAR/RAR4/RAR5 外部引擎与许可 | 同域后续 PR | 现有 RAR reviewer 参与了实现，或需要第二意见 |
| `reviewer:docs` | 文档一致性/状态口径 | 同域后续文档 PR | 需要独立事实核查 |
| `release-engineer` | CI、签名、安装包、发布 | 同一发布链 | 需要独立发布审计 |

> 领域 reviewer 是“槽位”，不是“每个 PR 一个”。同一领域连续多个 PR 应复用同一个 reviewer；
> 只有它参与了实现、或需要独立第二意见时，才换另一个**已有** reviewer。

## 3. 分配算法

每次派发任务前按顺序执行：

1. **列池**：调用 `list_agents`，按角色/领域和 `inactive` 状态筛选。
2. **匹配**：优先同角色 + 同领域 + 上下文仍相关；不要求完全相同的任务描述。
3. **复用**：用 `send_message` 发送新的任务包（目标、范围、输入文件、验收、禁止事项）。
   - 不需要重新粘贴整份仓库说明；只给变更点和必须重读的文件路径。
   - 明确“这是延续任务”，并说明上次结论/未完成项。
4. **冲突检查**：若该 agent 正忙，先判断是否真的需要并行；同类工作不要开第二个。
   - 可以等它完成；或把任务拆成不同角色（实现 vs 评审）。
5. **新建**：只有以下情况才用 `subagent` / `subagent_fork`：
   - 池里没有匹配角色；
   - 需要独立评审，且现有 reviewer 已参与该改动；
   - 需要与当前对话隔离的上下文（例如一次性大范围调研）；
   - 并行收益明显大于重复读仓库的成本。
6. **登记**：新建时 `description` 使用 `角色:领域` 前缀（如 `reviewer:rar`、`core-engineer:7z`），
   后续按这个标签复用。

## 4. 复用 vs 新建 vs fork

| 方式 | 上下文 | 适用 |
|---|---|---|
| `send_message` 给已有 agent | 保留该 agent 的历史上下文 | 同域后续任务、同一 reviewer 复审、实现者修评审意见 |
| `subagent` 新建 | 干净上下文，需要自包含 prompt | 独立评审、一次性调研、无合适槽位 |
| `subagent_fork` | 复制当前对话的已完成轮次 | 子任务强依赖本对话上下文，且不想让子 agent 重读 |
| `workflow` | 每个 `agent()` 都是新 agent | 3+ 独立方向的一次性 fan-out；**不适合**同域复用 |

`workflow` 没有“复用已有 agent”的入口；同域后续不要用 workflow 重开一套 plan/implement/review/verify。
小步迭代优先“一个常驻实现者 + 一个常驻 reviewer”。

## 5. 上下文预算

- **复用**适合：同一模块的连续 PR、同一 reviewer 的多次复审、同一格式的测试补充。
- **新建**适合：需要独立判断、避免被前一轮结论锚定、或领域跨度大。
- 给复用 agent 的消息只包含：
  - 本次目标/范围/验收；
  - 变更文件路径 + 必须重读的文档链接；
  - 上次结论和未完成项；
  - 明确“不要重读整个仓库/不要重复已完成的检查”。
- 不要把父对话全文、全部工具输出、无关任务塞给子 agent；那是上下文浪费。
- 同一 PR 不并行开两个 reviewer；需要第二意见时，串行换一个**未参与**的 reviewer。

## 6. 并发与生命周期

- 默认同时最多 **2 个实现 agent + 2 个评审 agent**；同类工作不并行重复。
- 任务完成后 agent 保持 `inactive`，不删除；下次同域任务直接复用。
- 一个槽位只保留一个“主” agent；出现重复时，保留最近有该领域上下文的，其他不再派发。
- 若 agent 的上下文已明显过期/矛盾（例如旧架构结论），不要强行复用；新建并在 prompt 里说明“旧结论已废弃”。

## 7. 审计清单

每次派发前自问：

- [ ] 池里是否已有同角色/同领域的 agent？
- [ ] 它是否 inactive、上下文仍相关？
- [ ] 这次任务是否真的需要新上下文（独立评审/隔离调研）？
- [ ] 是否会把整个父对话/无关文件塞给它？
- [ ] 新建的 label 是否带 `角色:领域`，下次能找回？
- [ ] 同一 PR 是否已经有 reviewer，避免重复评审？

## 8. 当前会话的落地方式

> 截至 2026-11-25，当前 DSH 会话约有 **18 个历史 agent**（研究、M0 评审、实现、
> W1/AES/RAR/RAR4/docs/guide reviewer、GPU 评估）。数量是运行时状态，不写入仓库；
> 具体 id 以 `list_agents` 为准。历史 agent 不一定有 `角色:领域` label，按 description/领域人工映射；
> 首次复用后，在新消息里补一句规范槽位，后续按该槽位找。

按以下方式收敛：

- 研究类：`researcher` 槽位，按主题复用，不重复开同一主题的调研。
- 实现类：`core-engineer:core`（含字典/ZIP/core）与 `core-engineer:cli` 各保留一个主实现者，
  共 2 个；后续修 bug/补测试回到对应实现者。
- 评审类：按 `reviewer:core`、`reviewer:rar`、`reviewer:docs` 等领域收敛；同域后续 PR 复用最近一个，
  只有它参与实现时才换另一个已有 reviewer。
- GPU/hashcat：`qa-engineer:gpu` 槽位，复用已有 GPU 评估 agent，不按 spike 重开。

> 具体 agent id 属于当前 DSH 会话状态，不写入仓库；用 `list_agents` 查看并按 label/领域匹配。
